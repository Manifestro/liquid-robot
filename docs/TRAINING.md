# Training operations

`gps_30_50` keeps the same GPS/gyro observations and known north-facing launch, changing goal placement to 30–50 m forward along the road generator's Z axis. Actual straight-line distance can be slightly longer on curved roads and is recorded per episode as `start_distance_m`. Use a 120 s episode limit. No new physics build is needed: the player already accepts these environment parameters. To test transferred weights without training, pass `steppe-evaluate --curriculum gps_30_50 --background --timeout 120 --time-scale 30 --seeds ...`. A curriculum override affects the test environment, not checkpoint weights.

Evaluation writes incremental `evaluation_status.json`, so completed-world counts are visible before the full summary is ready. Traces also record GPS speed/course, target direction and yaw rate for failure diagnosis.

Use the README commands or `steppe-train --help`. `straight` sets a 3–5 m goal directly ahead and a typical 20 s timeout. `gps_long` sets a 10–30 m road goal, starts facing north, and uses GPS position plus gyro/course estimated heading; use 90 s timeout. `navigation` retains the original ideal-goal task. The environment is procedurally reseeded per episode within the same map generator. Distance/curriculum and timeout must be explicit when comparing runs.

`--initialize-from` loads policy weights only, with a fresh optimizer and zero training counter. Initial policy is evaluated on final-test seeds before updates, then the same seeds are evaluated after the requested number of actions. New runs default to 30 odd final-test seeds (30001–30059); older checkpoints retain their recorded configuration. Override with `--eval-seeds`. A 30-world result is still limited to this simulator/curriculum.

By default, every approximately 10000 training actions, a separate Unity process evaluates 12 fixed validation worlds (10001–10023). This process uses worker-id + 100; reserve both ports. Training physics and recurrent memory remain in the original environment. `--validation-interval` changes the interval; 0 disables it. `--validation-seeds` changes its worlds; validation and final-test sets must be disjoint, nonnegative unique odd seeds. `--no-eval` disables all evaluations. Checks at step 0 and the final step are included. Validation adds wall time but does not count toward the training-action budget.

`best.pt` and `best.json` retain the checkpoint with highest validation success, then fewest collisions, then highest return. A later worse model cannot overwrite them. `latest.pt` still records the last update. Both latest and selected best receive final-test evaluations (`evaluation_final.json` and `evaluation_best.json`); neither final-test result selects the checkpoint. Logs are `validation.jsonl` and per-check directories under `validation/`. `--learning-rate` allows a smaller continuation rate without changing the algorithm or transferred weights; the default remains 3e-4.

The run manifest records hyperparameters, versions, device, Python source hashes, initialization checkpoint hash and Unity assembly hash. Exactly the requested number of action decisions is collected. Checkpoints are atomic; latest is saved each PPO update, numbered snapshots approximately every 1000 steps. Retention is currently unbounded: allow disk space or archive artifacts outside a running process. New run directories are mandatory.

`status.json` describes baseline/training/validating/evaluating/completed/failed. `updates.jsonl` contains optimizer metrics; `episodes.jsonl` completed training episodes. `baseline.json`, `evaluation_final.json` and `evaluation_best.json` summarize fixed-seed evaluations; trajectories and camera images are saved alongside them. `failure.json` records an exception. `summary.json` gives totals and selected-best metadata. `steppe-report` audits weights/metrics and renders comparisons for runs with baseline/final evaluation (not --no-eval smoke runs); its original plots refer to latest, while a separate paragraph reports best.

Training losses do not establish driving quality. Track recent success, collisions, timeout count, return, route completion and held-out performance. `steppe-monitor` reads existing logs and emits TensorBoard data without changing training. It stops after a terminal status; the TensorBoard server can remain available.

PPO: 256-step rollouts, sequences of 32 plus 8 burn-in, batch of 4 sequences, 4 epochs, gamma .99, lambda .95, clip .2, Adam 3e-4, entropy coefficient .005, norm cap .5, KL early stop .03. Hidden state before the burn-in window is from the rollout policy (truncated BPTT). Timeout bootstrap uses the old episode's terminal observation and memory; all boundaries break GAE and clear episode memory. After a policy update the current episode's history rebuilds memory under new weights. CfC uses the official ncps cell directly to preserve [B,1] dt broadcasting with ncps 1.0.1.

Exact mid-episode resume, multi-agent/vectorized collection, automatic curriculum progression, cloud artifact storage and robot transport are not implemented. Seed repeatability is supported, but GPU and Unity physics do not promise bitwise determinism. Simulator `-batchmode` keeps graphics enabled for RGB.
